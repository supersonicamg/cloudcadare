UPI payments · /admin/payments/upi

  • Job: turn a screenshot into access, safely. One filled button: "Verify and unlock CEAP".
  • Queue = payment_proofs joined to orders + member. Default tab is Waiting, oldest first. A waiting item older than 24 h shows an Overdue chip. The sidebar badge counts waiting items.
  • Proof source: Uploaded (image shown in the panel) or WhatsApp (nothing to show; staff tick "I saw the screenshot on WhatsApp"). Staff can match a WhatsApp screenshot by the learner's phone number, shown in the row.
  • The panel auto-checks what it can: amount equals the order balance, note equals the order number, UTR not already used on another order (unique (gateway, gateway_payment_id) already exists), proof not older than the order.
  • Approve needs the tick "I can see this payment in our UPI app or bank statement". A screenshot can be faked; the money in the account cannot. Without the tick the button stays disabled.

What approve and reject do

  • Approve (one transaction, idempotent): payment → captured; if captured payments ≥ order total: order → paid, enrolment created (source = 'purchase'), receipt created; else order → partially_paid. Proof → approved with reviewer + time. Outbox: receipt email + WhatsApp.
  • Reject: needs a reason (amount_mismatch, not_received, screenshot_unclear, wrong_account, duplicate) and an optional note. Proof → rejected, order stays awaiting_payment, learner sees "needs action".
  • Permission: new payment.verify in the catalog, added to owner and finance roles; the action needs the authenticator step-up (sensitive) like refunds.
  • Every decision writes an audit row. Nobody can approve their own order (reviewer ≠ buyer).

Learner list (whitelist) · /admin/learner-list

  • Job: tell the system which existing learners already have CEAP, so they never pay again. One filled button: "Add to list".
  • New table access_whitelist (columns in plan/16 §3): email_norm (lower-case, trimmed), name, course_id, batch_id, expires_at, status (waiting / claimed / expired / removed), claimed_by, claimed_at, added_by, note. Unique per (tenant, email, course).
  • Add: paste emails (one per line, commas, or spreadsheet column) or import a CSV (email,name,batch,access_until). The result is explained: added, already on the list, looks wrong (no @ or domain). Nothing is silently dropped.
  • Matching rule: exact match after lower-casing and trimming. No "gmail dot" or "+tag" tricks, no wildcards, no whole domains (a domain wildcard would give everyone at a company free access).
  • Rows are removable only while waiting. A claimed row links to the learner and to their enrolment, where staff can end access.

Rules

  • The learner must confirm the email by code before the list is checked (Join flow, "Confirm email"). That is what makes an email-only list safe.
  • Access ends at expires_at (the enrolment gets the same date). Blank = the batch end plus the standard replay window.
  • Adding an email that already has an active enrolment (paid or not) changes nothing and says so.
  • Requires permission enrollment.manage + step-up, same as giving access by hand today.
  • Not yet decided: whether the owner can send an "your access is ready, sign up here" email from this screen (plan/16 §10).

Payment settings · /admin/payments (extends the page that exists today)

  • Job: set where learners pay and who they message. One filled button: "Save settings".
  • UPI card (new): UPI ID, name shown in the UPI app, QR mode, the WhatsApp number for screenshots, verification hours, and who is alerted when a payment arrives. Stored in tenant_settings.commerce.upi (JSON, no secrets, so no Vault). No change to payment_gateway_accounts, which stays for Razorpay and other keyed gateways.
  • QR mode: Make a QR for each order (default; amount and order number are inside it, learners cannot mistype) or Use my own QR image (a still image; learners type the amount and note themselves, so mismatches are more likely).
  • The UPI ID is validated by shape (name@bank) and the owner is asked to make one test payment of ₹1 to themselves before turning it on. "Live" is a switch: off hides UPI at checkout.
  • Razorpay card (today's form): stays, with the keys disabled and the badge Coming soon. A switch "Show Razorpay as Coming soon at checkout" is on. When the owner adds keys and flips it to Live, checkout offers it with no code change.

Rules

  • Changing the UPI ID never changes existing QR codes or orders; pending orders keep the ID they were created with (payments.raw stores it).
  • The WhatsApp number and hours are read from here by checkout, the waiting page, receipts and the header help line. One place, no hard-coded numbers.
  • Requires the same permission as the Razorpay form today, plus step-up.
